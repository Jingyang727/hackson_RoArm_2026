# 先验收网页抓放闭环

当前以 `/experiments` 为唯一验收入口，暂缓新增视觉API和OpenCode流程改造。网页本来就直接调用公司Grok API：一次场景检查发送原观察与计划预览，动作后一次发送时序关键帧；不依赖OpenCode子Agent或`@`路径展开。配置和凭据继续沿用现有公司API设置，页面过程显示实际调用模型及图片数量，原始公开回复、结构化结论和实际参数继续备份。

用户提供的13:03:32–13:04:53日志中，闭爪和抬升已完成，后段没有完成投放；Grok给出了抓空判断。旧逻辑只要遇到10秒窗口超时，就统一屏蔽所有视觉修正，而网页又没有选择单项执行试验，所以停在“没有新修正”。这不是没有可比前轮导致的停止。

现在按执行阶段选择学习依据：

- 闭爪、抬升均有完成事件，录像证据完整，Grok确认球仍在桌面；若是后续运输/投放超时，仍能基于这轮抓空图像修正抓取位置或高度。后段超时保留在记录里，10秒要求继续检查。
- 抓取阶段未完成，不能把未确认的动作误判成抓空。网页按执行诊断选择一个移动速度试验；移动速度到上限后才选择下探速度。每次只改一个参数。
- 实际运输间隙不足，按真实反馈建议选择一次抬升高度试验；没有有效高度或候选超出当前试验范围时明确停止，不降低桌面间隙。
- 抬升后录像确认球滑落时，优先学习夹持或运输策略，不因为后段也超时就反向加速。
- 所有网页候选参数经过新鲜状态与完整路径IK检查后保存；失败时保留视觉结论和明确的拒绝原因，不声称参数已更新。

`image_up`表示夹爪在目标的画面上方，应向画面下方修正平面位置。`too_high`只表示实际离桌高度过高，需要降低抓取高度；不能仅因像素位置在上方就判断高度过高。Grok提示与页面文字均明确区分。画面方向经保存的标定转换为机器人XY，再检查预计画面变化是否符合纠正方向，不直接写死“向下就是X增加”或再全局翻转Y。

页面显示决策依据、实际保存前后参数，以及标定计算的平面补偿变化。没有单项前后对照只表示不能归因上一轮效果，不妨碍依据本轮清晰画面开始一个新试验。没有可执行的新参数时，停止原因直接说明是路径不可达、速度上限、反馈不足或其他具体原因。

接口 `/api/bench/rsi/state` 保持 `api_version=10`。当前 `web_learning_version=3`、`minimum_xy_step_mm=10`，新版页面检测此字段，避免把旧服务误当成已加载新逻辑。[XY试验与落点审计](rsi-xy-trial-audit.md)说明至少10mm的自动步长、实际四轮数据和新的只读核对入口。

本机更新运行中的同一worktree，只重启普通用户网页服务，保留相机进程、当前标定、参数和试次。沿用原Gemini Python与 `EVOARM_ENABLE_MOTION=1 EVOARM_ENABLE_TEACH=1 EVOARM_SETUP_ID=bench-layout-v2`。确认上面两个版本字段及运动开关后，由用户在网页点击开始，按页面选择的轮数继续，成功即停。已有旧决策不改写，新任务重新观察并使用新试次ID。

自动化使用模拟硬件和模型回复验证：后段超时后的视觉修正进入第二轮、实际高度与画面上下分别学习、前段超时后速度试验落盘、低间隙试验保留原要求、不可达候选停止，以及真实HTTP客户端在一次请求中携带实际JPEG数据。它们验证软件链路，不证明实机成功率或公司Grok的视觉判断一定正确。
